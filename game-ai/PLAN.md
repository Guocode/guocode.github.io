# Pixel Arena · 一个 MoE 模型同时玩两个游戏

> 状态：**已实现并训练完成**。本文件记录最终设计、真实训练数据与踩坑过程。
> 在线页面：`/game-ai/`（GitHub Pages 静态托管）

---

## 1. 项目定位

用**一个** 22,473 参数的 MoE 策略网络，同时学会两个操作方式、状态语义、失败条件完全不同的游戏：

| | Game 00 · 机器人赛跑 | Game 01 · 失控汽车 |
| --- | --- | --- |
| 模型 | 躯干刚体（平动 + 俯仰）+ 两条弹簧腿 | Frenet 坐标 + 随机轮子失控扰动 |
| 键盘 | ← 迈左腿 / → 迈右腿 / ↑ 前倾 / ↓ 收身 | ← 左打方向 / → 右打方向 / ↑ 油门 / ↓ 刹车 |
| 失败 | 俯仰超过 52° 或躯干触地 | 冲出路面，或车速低于 0.6 m/s |
| 回合上限 | 25 s（1500 步 @ 60 Hz） | 同 |

两个环境都是自己写的轻量物理，Python（训练，向量化）与 JavaScript（浏览器，单实例）各实现一份，
共用同一套常量与积分公式。

---

## 2. 为什么能共用一个模型

* 两个游戏都是 **4 个离散动作 / 14 维观测 / 60 Hz**，接口完全对齐
* 观测语义靠 2 维任务 one-hot 区分，喂给 router 做路由依据
* 奖励都以前进距离为主项，尺度可比（advantage 仍按任务分别归一化）

---

## 3. 模型架构（MoE）

```
obs(14) + task one-hot(2)
  → shared trunk   16 → 64 → 64   (Tanh)
  → router         64 → 4         → top-2 softmax 门控
  → 4 个 expert    64 → 64        (Tanh)，按门控加权求和
  → actor(64→4) + critic(64→1)
```

* 参数量 22,473，权重 118 KB（base64 编码的 float32）
* 浏览器端**手写前向**（`assets/js/moe.js`），零依赖，首屏即用；
  与 PyTorch 输出最大误差 **1.9e-6**
* `train/export_onnx.py` 可导出标准 ONNX（需 `pip install onnx`，本地网络受限未生成）

---

## 4. 训练设置

* 算法：多任务 PPO（`γ=0.99, λ=0.95, clip=0.2, lr=1.5e-4, 4 epochs, mb=1024`）
* 规模：两个环境各 32 个并行实例，500 次更新，纯 CPU **11 分钟**
* **行为克隆预热**：先用启发式策略采 3 万条示范做监督学习（准确率 92.8%），
  再交给 PPO 微调——交替迈腿这类组合动作靠随机探索几乎发现不了
* Switch Transformer 负载均衡损失（系数 0.01），防止路由坍缩
* 保存综合得分最高的 checkpoint（`runner/80 + car/200`）

## 5. 结果（32 回合评估，单回合上限 25 s）

| 策略 | 机器人赛跑 | 汽车驾驶 |
| --- | --- | --- |
| **MoE（本项目）** | **88.07 m**（摔倒 0%） | **543.97 m**（失败 0%） |
| 启发式规则 | 80.67 m | 148.62 m |
| 随机动作 | 5.41 m | 10.52 m |

### 专家专业化（自己涌现，未人工指定）

| 专家 | 机器人使用率 | 汽车使用率 |
| --- | --- | --- |
| Expert 0 | **90.3%** | 0% |
| Expert 1 | 0% | **99.8%** |
| Expert 2 | 9.7% | 0.1% |
| Expert 3 | 0% | 0% |

两个游戏几乎完全走不同专家，但共享同一个 trunk 和输出头。

### 架构消融（等参数量对照）

另训了一个普通 MLP（20,741 参数，无专家无路由），同样的训练流程：

| 架构 | 参数量 | 机器人 | 汽车 |
| --- | --- | --- | --- |
| MoE (top-2) | 22,473 | **88.1 m** | **544.0 m** |
| 普通 MLP | 20,741 | 68.3 m | 365.6 m |

MLP 的机器人成绩从更新 50 起就卡在 68.3 m 不动（两个任务的梯度互相干扰），
汽车在 23–336 m 之间剧烈震荡。**MoE 在两个任务上都明显更优。**

## 6. 踩过的坑（物理是反复改出来的）

机器人环境的调试过程，每一步都是先定位根因再修：

1. **机器人只会倒退** → 弹簧水平分力在前腿处形成无法摆脱的制动，且推进力弱于阻力。
   改为「弹簧只负责垂直支撑，水平完全由蹬地推进驱动」。
2. **站着不动也能滑行很远** → 蹬地推进与腿的静态压缩绑定。改为「蹬地能量」机制：
   每条腿落地时充满能量、支撑期间 0.3 s 内耗尽，不换步就跑不动。
3. **速度失控到 10 m/s 后被压垮** → 推进力与速度无关。加入随速度衰减的推进上限
   （`V_CUT=5`，模拟步频的生理极限）。
4. **腿被拉过头会把身体拽倒** → 加入被动拖离：腿伸过头自动离地换步，
   但**不**重置蹬地能量，所以主动换步才是维持速度的关键。
5. **前几步就摔倒** → 弹簧刚度太低，双腿/单腿切换时身体塌陷 0.2 m。提高到
   `K_LEG=800`，切换时只下沉约 1 cm。
6. **俯仰控制与迈腿互相抢占动作位** → 姿态控制改为「设定目标倾角」的高层指令，
   由内部 PD 伺服（`KP=14, KD=2.6`）持续执行，不占用迈腿动作。

汽车环境一次成型，未做大改。

## 7. 跨端一致性验证

`node tools/check_js.mjs`（开发用）：

```
runner alt-step   mean 78.75  std 0.02  [78.71, 78.80]
car lane-keeping  mean 145.52  std 59.53 [26.58, 233.64]
  (python ref:   runner 78.75±0.03 | car 134.88±66.34)
moe.js vs torch   max abs err = 1.91e-06  (OK)
```

机器人成绩两端完全相同；汽车因失控事件依赖随机数流（Python 为向量化批量预生成、JS 为流式取数）
无法逐位一致，取统计一致性（均值在同一量级，方差接近）。

## 8. 目录结构

```
game-ai/
├── index.html              展示页（像素风，零框架）
├── PLAN.md                 本文档
├── assets/
│   ├── img/versus.gif      AI vs HUMAN 对战回放（record_gif.py 生成）

    ├── model.py            MoEPolicy / MLPPolicy（对照）
    ├── train_moe.py        多任务 PPO（--arch moe|mlp）
    ├── export_onnx.py      导出权重 / ONNX / 页面指标
    ├── record_gif.py       录制 AI vs HUMAN 对战回放 GIF
    ├── verify.py           生成跨端验证参考数据
    └── ckpt/               moe.pt · mlp.pt · *_history.json
```

## 9. 复现

```bash
pip install torch numpy
python train/train_moe.py --updates 500 --lr 1.5e-4          # 约 11 分钟（CPU）
python train/train_moe.py --arch mlp --updates 500           # 对照实验（可选）
python train/export_onnx.py                                 # 导出权重与页面指标
python train/record_gif.py                                 # AI vs HUMAN 回放 GIF
python train/verify.py && node tools/check_js.mjs           # 跨端一致性

# 本地预览
cd game-ai && python -m http.server 8080                     # 访问 /game-ai/
```
